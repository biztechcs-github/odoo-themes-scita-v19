---
name: "OPSX: Capability Map"
description: Decompose a product brief or SOW into a prioritised capability map before proposing
category: Workflow
tags: [workflow, planning, capability-map]
---

Decompose a product brief, scope document, or set of wireframes into a structured capability map — the ordered list of capabilities that will become individual OpenSpec changes.

Use this command between project install and the first `/opsx:propose`. Without a capability map, large products get proposed as one unmanageable change instead of a sequence of well-scoped, dependency-ordered changes.

**Store selection:** If the work lives in a registered store, pass `--store <id>` on any OpenSpec commands below.

**Input**: One or more of the following:
- A product brief, scope document, or SOW (paste content or provide file path)
- Wireframe screens (file paths or descriptions)
- A problem statement and high-level feature list

If none provided, ask the user to share the brief or scope document before proceeding.

---

**Steps**

1. **Read the input materials**

   Read every document or file the user provides. If wireframe files are referenced, read them.

   From the materials, extract:
   - The product's primary purpose and user types
   - The features, screens, and workflows described
   - Any explicit phases or priorities mentioned
   - Constraints: tech stack, integrations, non-goals

2. **Identify capabilities**

   A capability is a cohesive unit of user-facing or system behaviour that:
   - Can be independently proposed, specced, and built
   - Has a clear boundary (you know when it's done)
   - Delivers value on its own or unlocks the next capability

   Rules for splitting:
   - Split by user type if the same feature looks different for different roles
   - Split by data entity if each has its own CRUD lifecycle
   - Split cross-cutting concerns (auth, multi-tenancy, i18n) into their own capabilities
   - Do NOT split a single screen into multiple capabilities (keep screens together)
   - Do NOT merge unrelated features into one capability to keep the count low

   Assign each capability:
   - A kebab-case name (this becomes the `specs/<name>/` folder)
   - A one-line description
   - A type: `foundation` / `feature` / `integration` / `infrastructure`
   - A complexity estimate: `S` (< 1 day), `M` (1-3 days), `L` (3-5 days), `XL` (> 5 days)

3. **Map dependencies**

   For each capability, identify which other capabilities it depends on (must be built first).

   Common dependency patterns:
   - Auth / login → everything that requires a logged-in user
   - Multi-tenancy / data isolation → every feature that stores tenant data
   - Core entity CRUD → features that reference that entity
   - API contract → both sides of any client-server split

   Mark cross-cutting concerns (`foundation` type) as dependencies for all features that use them.

4. **Produce the capability map**

   Output a structured `capability-map.md` document. Write it to the repo root (or `openspec/` if preferred — ask the user).

   Format:

   ```markdown
   # Capability Map — <Project Name>
   <!-- Generated by /opsx:capability-map — edit as the project evolves -->

   ## Product Summary
   <2-3 sentences: what is being built, who uses it, what problem it solves>

   ## User Types
   - **<UserType>**: <one-line description of their role>

   ## Capability Inventory

   | # | Capability | Type | Complexity | Depends On |
   |---|------------|------|------------|------------|
   | 1 | `<kebab-name>` | foundation | M | — |
   | 2 | `<kebab-name>` | feature | L | 1 |

   ## Build Order (dependency-resolved)

   ### Phase 1 — Foundation
   - [ ] `<cap-1>`: <description> — *<complexity>*
   - [ ] `<cap-2>`: <description> — *<complexity>*

   ### Phase 2 — Core Features
   - [ ] `<cap-3>`: <description> — *<complexity>*

   ### Phase N — ...

   ## Parked (out of scope for now)
   - `<cap-name>`: <why parked>

   ## Open Questions
   - <Any architectural or scope question that must be answered before proposing>

   ## Next Step
   Start with the first unchecked capability in Phase 1.
   Run: `/opsx:propose "<cap-name>" — <one-line description>`
   ```

5. **Confirm with the user**

   Present the capability map and ask:
   - "Does this match your understanding of the scope?"
   - "Are any capabilities missing, misnamed, or should be merged/split?"
   - "Is the Phase 1 foundation list correct — are there any other cross-cutting concerns?"

   Revise the map based on feedback before writing the file.

6. **Write the file**

   Once the user confirms, write `capability-map.md` to the agreed location.

   Tell the user: "Start proposing capabilities in Phase 1 order. Run `/opsx:propose` for the first unchecked capability when ready."

---

**Output Example**

```
## Capability Map — NFCWine

### Phase 1 — Foundation
- [ ] `auth-roles`: Platform Admin / Client Manager / Operator auth + RBAC — *M*
- [ ] `tenant-isolation`: Multi-tenant data model + row-level isolation — *L*
- [ ] `industry-field-schema`: Data-driven field engine (Food vs Cosmetics) — *XL*

### Phase 2 — Core Features
- [ ] `client-onboarding`: Platform Admin creates and configures a client tenant — *M*
- [ ] `batch-management`: Client Manager creates and manages product batches — *L*
- [ ] `chip-registration`: Operator assigns NFC chips to batch items — *M*

### Phase 3 — Consumer & Scan
- [ ] `consumer-page`: Public EN/IT traceability page rendered on NFC tap — *L*
- [ ] `mobile-scan`: Flutter scan app with offline sync + duplicate detection — *XL*

Next: `/opsx:propose "auth-roles — Platform Admin / Client Manager / Operator RBAC"`
```

---

**Guardrails**
- Never start with feature capabilities before foundation capabilities are listed
- Never merge auth, multi-tenancy, or i18n into a feature capability
- Never produce a map with fewer than 3 or more than 20 capabilities for a single project
  (fewer means under-decomposed; more means a phase split is needed)
- Always ask for user confirmation before writing the file
- If the input is too vague to produce a map, ask for the scope document rather than guessing
